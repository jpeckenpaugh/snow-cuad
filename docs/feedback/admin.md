## Liked
1. **Provisioning genuinely works end to end.** I created `test-user-01` as `lawyer`, and the one-time password `[redacted one-time password]` signed me into a *different tab* first try — and the new account landed in the correct role view (browse pages only, no Reports/Admin). The generated password is shown exactly once via a `st.code` block and is never stored; that matches the intent in `admin.py`.
2. **Suspension really bites — including a live session.** A suspended account is refused at login, *and* an already-signed-in session is cut off on its next interaction with a clear message ("Your session has ended because the account is no longer active.") and a `SESSION_REVOKED` audit row. An admin who suspends someone can trust that it took effect, not merely that it will at next login.
3. **"Never delete" is real, and the UI explains it.** Suspension is a status change: the row, `DISPLAY_NAME`, role and audit history all survive, and the caption *"Suspended accounts keep their row and their audit history; only login is blocked."* tells the operator why there is no delete. This is enforced below the UI too (the service role has no `DELETE` grant on `APP_USERS`).
4. **Self-lockout is prevented twice over.** The caption says you cannot suspend your own account, and `admin` is silently absent from the Manage picker, so the footgun is unreachable rather than merely discouraged. As the persona literally named "admin", I can't accidentally lock myself out.
5. **The Reports surface is real and honest.** Logins gives Events/Successes/Failures/Last success per username *and* recent failures with a Reason column — I saw `test-user-01 / lawyer / account suspended` and could see it was my own suspend action. Searches logs terms verbatim, Documents resolves titles, and Activity shows the whole stream (I could see other sessions' work, e.g. an `auditor` `REPORT_RUN` and `lawyer-001` searching `change of control` at 08:42:57). Every table exports faithfully as CSV.

## Frustrated by
1. **The Users table is unreadable as a table.** It is a canvas grid: the cell text is not selectable, it is absent from the accessibility tree until you click in and move focus, and at the default width the **Last login (UTC)** column is scrolled off-screen (I could only read it after forcing `scrollLeft` to 730px; the fixed column widths total 730px inside a ~538px container). For the single most important admin artefact — "who exists, in what role, last seen when" — I had to fight the widget to get five numbers.
2. **The Manage picker resets after every action.** After I clicked *Suspend test-user-01*, the page reran and the Account selectbox jumped back to `auditor · Tomas Beck · auditor · active`; after *Reactivate* it did the same. Every suspend/reactivate/reset therefore costs a re-selection, and there is no per-row action — you manage exactly one account at a time through a dropdown.
3. **A suspended login is indistinguishable from a typo in the moment.** As the admin who had *just* suspended `test-user-01`, attempting to sign in as it returned the same **"Invalid username or password."** as a bad password. The real reason ("account suspended") appears only in the Logins report / audit log, so the console gives the operator no immediate confirmation that the block is for the reason they think.
4. **Almost nothing about a user is editable or inspectable.** No delete, no edit-role, no edit display name, no change-password, no bulk actions, no user search/filter/pagination, and no per-user detail view. The console never shows *who* suspended an account or *when*, even though `SUSPENDED_BY` and `SUSPENDED_AT` are stored (I could only see them by querying the table). Any admin can also silently mint another `admin` — there is no approval or audit gate beyond the `USER_CREATED` line.
5. **The one-time password is a flash that disappears on the next click.** It is shown once in `st.code` and popped from session state; the moment you click anything else (e.g. moving on to Suspend) it is gone, and there is no "show again", no re-issue that avoids invalidating the old one, and no indication of expiry. Miss the copy and you must do a full password reset — which is exactly the loop I hit between creating the user and testing it.

## The one thing I'd add first
Replace the "pick one account from a dropdown, then click one button" Manage block with a proper per-user detail view: click a user row and get a panel showing role, status, created, last login, suspended-by/at, and their recent audit events, with row- or panel-level actions to suspend/reactivate, reset password, and change role. Almost all of the data already exists (`SUSPENDED_BY`, `SUSPENDED_AT`, `LAST_LOGIN`, the `ACCESS_LOG` stream) — it is simply never surfaced. That one change turns the console from a one-at-a-time lever into something an admin would actually trust during an incident, when the question is not "suspend this person" but "what is going on with this account, right now".

## Honest limits I noticed
- **All app logins share one Snowflake session.** Layer 3 is application-level: the app connects as the single `STREAMLITWEB` service identity, so Snowflake RBAC cannot separate one lawyer from another and `LOGIN_HISTORY` will only ever show `STREAMLITWEB`. Roles gate *pages* in the app, not data.
- **No document-level access control.** Every lawyer sees the whole 510-contract corpus; the README says so explicitly, and the new `test-user-01` got the same unfiltered browse pages as everyone else.
- **The access log is application-level, not tamper-proof.** Writes go through the same service role the app uses; the role holds `INSERT` only (no `UPDATE`/`DELETE`, which I confirmed the design of in `docs/security.md` / `sql/07_audit.sql`), but anyone holding that role's credentials could append rows, and `ACCOUNTADMIN` owns the table outright.
- **No delete path for users.** Not an oversight — deliberate, enforced by withholding the `DELETE` grant on `APP_USERS`, and explained in the UI. But it does mean a typo'd account (like my `test-user-01` if it were a mistake) can only ever be suspended, never removed.
- **The console has no self-service or policy surface:** no self-service password change, no password policy/expiry/rotation, no MFA, no "sessions" list or explicit force-logout button (revocation happens implicitly when status changes), and no inbox/invite flow — the admin must hand over the one-time password out-of-band.
- **Search terms and attempted usernames are stored verbatim** in `ACCESS_LOG.DETAIL` (I read `governing law`, `indemnif`, `agreement` straight out of the CSVs), so the audit trail can accumulate sensitive query text with no redaction.
- **The Users grid is canvas-rendered**, so as observed its values are not selectable, copyable, or exposed to assistive technology without keyboard focus — a real accessibility limitation for an admin tool.
- **I could not take screenshots.** The browser screenshot tool repeatedly failed with "Screenshot needs a visible tab / keep its desktop window visible", so my table values come from the focused grid's accessibility tree and were cross-checked against the app's own read path (the exact `SELECT` in `admin.py`); both agreed.
